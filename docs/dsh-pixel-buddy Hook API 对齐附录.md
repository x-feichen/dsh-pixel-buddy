## 2. 内部事件契约（适配层归一化目标）

适配层将 Hook API 原始事件归一化为以下内部枚举。**状态机（T1.4）只依赖本契约，不感知 DSH 事件命名**——这是隔离外部不确定性的架构边界。

```ts
/** 内部会话事件（由事件适配层产出） */
type SessionEvent =
  | { type: 'task-start' } // 一次请求开始处理（对应"运行中"起点）
  | { type: 'task-success' } // 请求正常结束（对应"成功"）
  | { type: 'task-error' } // 请求异常结束（对应"报错"）
  | { type: 'input-required' }; // 需要用户介入（对应"需要人工"，澄清结论 D4）

/** 宠物状态（状态机输出，渲染层输入） */
type BuddyState = 'idle' | 'running' | 'input-required' | 'error' | 'success';
```

约束：

1. 事件均为**请求级**（澄清结论 D3：单次请求粒度），不包含流式中间事件。
2. `task-start` 后必须存在且仅存在一个终态事件（`task-success` / `task-error`）；`input-required` 为运行中任务内的分支信号，之后仍以终态事件收尾。
3. 适配层对上保证事件有序、去重；乱序/重复事件由适配层丢弃（见 §3.3）。

## 3. 事件适配层规范（T1.3 的实现依据）

### 3.1 职责边界

```
DSH Hook API ──► 事件适配层 ──► 内部事件契约 ──► 状态机(T1.4) ──► 渲染层(T1.5)
                 （唯一允许感知 DSH 的模块）
```

- 适配层是**唯一** import DSH 插件全局对象/API 的模块，其余模块只依赖内部契约 → API 变化只改适配层。
- 适配层同时负责：事件名映射、参数归一化、异常兜底、订阅生命周期（插件卸载时解绑）。

### 3.2 事件映射（⚠️ 右列为占位命名，以 §5 核实结果回填）

| 内部事件         | DSH Hook API 原始事件（占位）            | 置信依据                      |
| ---------------- | ---------------------------------------- | ----------------------------- |
| `task-start`     | `stream:start` / `task:start`            | PRD §4.2 示例                 |
| `task-success`   | `stream:end`（正常结束）                 | PRD §4.2 示例                 |
| `task-error`     | `error` / `stream:error`                 | PRD §4.2 示例                 |
| `input-required` | `confirmation:request` / `input:request` | 澄清结论 D4，**不确定性最高** |

### 3.3 归一化规则

- **去抖**：同一 `type` 事件 200ms 内重复触发，仅透传一次（与澄清结论 D2 一致；去抖定时器为单次 `setTimeout`，非轮询）。
- **乱序防护**：未收到 `task-start` 时收到的终态事件丢弃并上报 warn 日志（防宿主晚加载导致脏事件）。
- **粘滞协同**：适配层不做粘滞判断，粘滞/优先级全部由状态机负责（单一职责，避免双处记账）。

### 3.4 降级约定（API 不可用/事件流中断）

| 场景                                                | 行为                                                                                                       |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Hook API 对象不存在（插件加载早于宿主注入）         | 延迟重试绑定：`setTimeout` 退避重试（1s/2s/4s/8s，上限 3 次），仍失败则静默待机，不报错不打扰用户          |
| 订阅后 API 抛异常                                   | 捕获、卸载订阅、静默回退待机；**不向宿主页面抛出未捕获异常**（T1.3 验收项）                                |
| `task-start` 后终态事件丢失（如 `stream:end` 丢失） | 状态机侧超时降级：单次 `setTimeout`（建议 10min，常量可调）后强制回待机；**不引入轮询**（PRD §5 性能红线） |
| 页面刷新                                            | 无快照时：宠物回待机（可接受的保守降级）；若 §5-6 核实 API 提供状态快照查询，则升级为精确恢复              |

## 4. 插件侧接口定义（T1.3 按此先行开发）

```ts
/** 事件适配层对状态机暴露的接口 —— T0.3 技术形态确认后此签名冻结 */
interface SessionEventAdapter {
  /** 订阅内部事件；返回解绑函数，插件卸载时必须调用 */
  subscribe(listener: (e: SessionEvent) => void): () => void;
}
```

- 实现为 `DshHookAdapter implements SessionEventAdapter`，构造时注入宿主 API 获取函数（便于单测注入 mock，不依赖真实宿主）。
- 单测用 mock 适配层驱动状态机（T1.4 与 T1.3 并行的前提，对应规划 §4.1"接口契约先行"）。

## 7. 回填记录：真实 DSH 插件系统（v1.0，2026-09-05 实测回填）

> 已在真实环境（`@deepseek-ai/dsh@0.1.0-rc.8`，web profile）安装并端到端验证。**实际接入形态与 §2/§3 的"Hook 事件"假设不同**，以本节为准：

| # | 核实项 | 真实结论 |
|---|---|---|
| 1 | 事件获取方式 | DSH 无 Hook 事件订阅 API；插件以**客户端模块**形态接入（package.json `dsh.client` + `exports["./client"]`），占用 `conversation.session.header.utilities` 座位，经框架注入的 `useSession` 快照 hook 读取 `ConversationSnapshot` |
| 2 | "需要人工"事件 | 存在：`snapshot.pending`（PendingInteraction[]，权限确认/用户提问等），D4 裁决的三类场景成立 |
| 3 | 会话上下文 | 座位按会话实例挂载（携带 sessionId）；多会话经聚合引擎按优先级收敛（T3.2 §3 最小实现） |
| 4 | 顺序性/终态可靠性 | 快照为状态面而非事件流，无丢失问题；`task-start` 后终态由 running→idle 转移派生 |
| 5 | 错误详情 | `snapshot.promptError` 非空即错误；详情未读取（本期不需要） |
| 6 | 状态快照 | 天然具备（快照即状态面）；刷新后由快照直接恢复真实状态，优于保守降级方案 |
| 7/8 | 加载时序/卸载 | 座位随会话视图挂载/卸载，destroy 生命周期已验证 |

**事件派生规则（实现于 `src/dsh/client.ts`）**：`error ← promptError`；`input-required ← pending`；`running ← running/partial/runningCalls`；`idle ← 其余`；粘滞徽章在宿主侧解除（用户在 DSH UI 完成确认/回答）时以 `user-ack` 清位，符合澄清结论 D2 精神。

**实测记录**：安装→bundle 服务→宠物挂载（会话打开时）→发消息 running 蓝点→success 绿勾→2.5s 自动淡出 idle，全链路通过；服务端零报错。
