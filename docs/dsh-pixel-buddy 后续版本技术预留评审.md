## 1. 评审结论（TL;DR）

MVP 架构**已为多会话预留了正确的扩展缝**：`SessionEventAdapter` 接口与状态机之间是纯函数边界，多会话能力可以以"新适配器实现"的形态加入，**状态机与渲染层无需重写**，但需要一次中等规模的状态层升级（单实例 → 会话表 + 聚合策略）。预估 3~5 人天（含测试）。

## 2. 现状边界盘点（哪些能直接复用）

| 模块 | 复用性 | 说明 |
|---|---|---|
| 契约（`SessionEvent`/`BuddyState`） | ✅ 原样复用 | 需增加可选 `sessionId` 字段（向后兼容：缺省视为单会话） |
| 状态机 reducer | ✅ 原样复用 | 每个会话一个 reducer 实例，粘滞/优先级逻辑不变 |
| 渲染层（徽章/主题/动效） | ✅ 原样复用 | 聚合决策产物仍是单个 `BuddyState` |
| 适配层 | ⚠️ 需新增 | 新增 `MultiSessionAdapter`：按 sessionId 分发事件到会话子状态机 |
| 聚合策略 | ❌ 全新 | 核心新增点，见 §3 |
| 展示层 | ❌ 全新 | 多会话聚合提示（如角标数字/队列点），PRD §9 已列为后续范围 |

## 3. 聚合策略设计建议（评审重点）

多会话收敛为单徽章的展示优先级，建议在澄清结论 D2 的粘滞语义上做如下扩展（**待产品裁决，本评审仅给建议**）：

1. **粘滞优先**：任一会话存在报错 → 展示报错（与单会话优先级一致）；
2. **需要人工计数**：多个会话等待人工时，徽章旁出现计数角标（如 `?×2`）；
3. **运行中取最新**：无粘滞时显示最近活跃会话的状态；
4. **每会话粘滞位独立**：消除交互需解决"点的是哪个会话"——建议单击消除**最高优先级粘滞位**，长按/后续版本悬浮卡片实现按会话消除。

**关键风险**：多会话下"单击消除"的语义变复杂，是后续版本需求评审的主要议题；MVP 的 `user-ack` 事件形态（无会话参数）可平滑升级为 `{ type: 'user-ack', sessionId? }`。

## 4. 改造点与预估

| 改造 | 规模 | 依赖 |
|---|---|---|
| 契约增加 `sessionId`（可选字段） | 0.5 人天 | 核实清单 #3（API 是否携带会话上下文） |
| `MultiSessionAdapter` + 会话子状态机表 | 1~2 人天 | 同上 |
| 聚合 reducer（会话表 → 展示态） | 1 人天 | 产品裁决 §3 策略 |
| 聚合展示（角标）+ 测试 + fuzz 扩展 | 1~1.5 人天 | 美术需求（角标样式） |

**前置依赖（硬）**：Hook API 核实清单 #3——若 DSH 事件不携带会话上下文，则多会话在本插件侧不可实现，只能做多标签页聚合（`BroadcastChannel`/`localStorage` 跨页同步，另评）。

## 5. 其他后续版本方向的技术预留状态

| 方向（PRD §9） | 现有预留 | 缺口 |
|---|---|---|
| 点击互动（拖拽/右键/悬浮卡片） | 容器层已有点击事件通道（D1 例外） | 悬浮卡片需脱离 Shadow DOM 定位策略评审 |
| 养成/个性化（皮肤/心情值） | 美术需求单要求分层源文件；资产接入层单点可替换 | 需状态持久化方案（引入存储，需重评"零存储"边界） |
| 任务完成后台通知 | live region 基础设施可复用 | 需 Notification API 权限流程，独立需求评审 |
