## 2. 裁决详情

### D1. 消除途径：采用"点击宠物即消除"最小方案

- **裁决**：在宠物本体处于"报错"或"需要人工"徽章状态时，**单击宠物本体即确认并消除徽章**，回到待机态。除此之外不引入任何其他交互（无拖拽、无右键、无悬浮卡片）。
- **理由**：
  1. PRD §4.6 与 §7 验收 4/5 均要求"用户主动交互后才转回待机"，宿主页面操作自动解除的方案无法覆盖"会话已死、无后续事件"的场景（如报错后用户放弃该任务），必须有插件自身的消除入口；
  2. 点击是成本最低、不与"点击互动系统"（悬浮卡片、菜单等）产生范围蔓延的最小交互。
- **配套修订**：PRD §1.3 范围声明修订为——"点击互动能力不在本期范围；**唯一例外**：报错/需要人工状态下，单击宠物本体用于确认消除徽章（见 §4.6）"。此例外在后续版本扩展点击互动时保持兼容。

### D2. 粘滞规则与优先级的交互（状态机边界行为）

粘滞态（报错、需要人工）期间收到新的会话事件时，按下表处理——**原则：粘滞态只被用户点击消除，不被任何自动事件覆盖或自动清除**：

| 粘滞态              | 新事件                 | 徽章表现             | 说明                                                                                      |
| ------------------- | ---------------------- | -------------------- | ----------------------------------------------------------------------------------------- |
| 报错                | `运行中`（新任务开始） | **保持报错**         | 高优先级粘滞态压制运行中；新任务照常在底层执行，不因徽章粘滞而中断                        |
| 报错                | `成功`                 | **保持报错**         | 新任务的正常结束不自动洗白上一次错误                                                      |
| 报错                | 新的`报错`             | 保持报错（刷新计时） | 重复报错合并，不闪烁                                                                      |
| 需要人工            | `运行中`/`成功`        | **保持需要人工**     | 同上；需要人工表明存在等待用户的待办                                                      |
| 报错 + 需要人工并存 | —                      | 显示报错             | 优先级：报错 > 需要人工；两个粘滞位独立记账，消除报错后若需要人工仍存在则切换显示需要人工 |
| 任一粘滞态          | 用户单击               | 回到待机             | 同时清除对应粘滞位；若另一粘滞位仍存在则显示之                                            |

- **去抖/合并**：同一状态事件在 200ms 内重复触发视为一次（防闪烁，对应验收 6）；爆发事件序列按优先级仲裁后只做一次 crossfade。

### D3. 会话粒度：单次请求/任务

- 状态粒度 = **一次用户请求从发起到结束的完整生命周期**（对应 `stream:start` → 终态）。一个对话包含多次请求，宠物反映**最近一次请求**的状态。
- 请求结束（成功/报错）后进入终态展示期，随后按 §4.6 规则回待机；下一次请求开始即切"运行中"。
- 多标签页/多会话：**MVP 仅反映当前激活标签页的会话**，不做跨标签页聚合（T3.2 评审多会话抽象，本期不实现）。

### D4. "需要人工"触发场景

- **定义**：DSH 在任务执行中需要用户主动介入才能继续的场景，MVP 收敛为三类：① 权限/操作确认（如危险命令确认）；② 审批/授权请求；③ 模型明确请求用户补充输入。
- **事件契约（占位，T0.2 核实）**：对应 Hook API 的 `confirmation:request` / `input:request` 类事件。
- **风险与兜底**（规划文档 R1）：若 T0.2 摸底发现 API 不提供此类事件，则该状态降级为 P1 并从 MVP 状态模型裁剪（5 态变 4 态），PRD 同步修订。**此兜底方案即为书面预案，无需再次评审。**

### D5. 交互参数初值

- 徽章 crossfade 过渡时长：**150ms**（PRD 建议区间内取上限，小尺寸下更不易被察觉为闪烁）。
- "成功"徽章最短展示时长：**2.5s**，到期后自动淡出回待机。
- 两者在代码中以命名常量实现，T2.6 体验验证后可调，调整不改架构。
